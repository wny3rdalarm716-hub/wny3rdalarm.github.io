# V2.4 — Staff portal setup

## Install files
Back up the existing app. Extract this patch at the repository root, merging the app/ folder. Do not delete the old app/ folder. The existing photos, icons, manifest, reviewed-incidents.json, main website, voting and push registration remain untouched. No credentials are included. Before Firebase is configured, the staff portal shows a setup-required message and the public app operates normally.

## 1. Create a dedicated Firebase project
Use https://console.firebase.google.com/ to create a new project for the admin portal (for example, WNY 3RD ALARM Admin). Keep the existing wny-photo-of-the-week project for voting and push tests. Use Spark if available and do not enable paid services without understanding the costs. Register a Web app and copy its public firebaseConfig object into app/admin-config.js, replacing the empty config object. Do not paste passwords or service account keys. Enable Email/Password in Authentication > Sign-in method. Add wny3rdalarm716-hub.github.io as an authorized domain if needed for authentication. Create a Cloud Firestore database in production mode in the new project.

## 2. Publish and test rules
In the NEW project's Firestore > Rules, replace the initial rules with the exact contents of app/firestore.rules. Do NOT publish these rules to the existing voting project. Review the rules, then publish them. They deny writes by default; the only public readable documents are fixed app settings and historical summaries. The project owner must verify the rules in the Firebase Rules Playground or Emulator before allowing public access. Do not change rules to test mode. Rules have not been run against a live Firebase project by the author of this patch.

## 3. Authorize the three staff accounts
In Authentication > Users, add one email/password account per staff member. Use email addresses they control, do not share accounts/passwords. Have each person set their own password using the portal's password reset email flow and verify their own email from the sign-in page. Copy each account's Firebase UID from the Users list. In Firestore > Data, create a collection named staffAccess. For EACH account, add one document whose document ID is that account's exact UID. Add the field active (Boolean) = true. Tony, Lily and Quinn all have identical permissions. Do not include names, emails or passwords in the access documents. To revoke staff access, set active = false or delete that person's document and disable the Authentication user if appropriate. Do not use email addresses as document IDs. The project owner provisions accounts through Firebase console; the client cannot modify staffAccess or create privileged accounts. Do not grant broad Firebase project-owner permissions just to use the portal.

## 4. Test and deploy
Open /app/admin/ from Settings > Open Admin Panel. Verify that an anonymous visitor cannot access controls, a verified but unlisted account cannot read drafts or write app settings, and all three authorized accounts can save a preset announcement. Confirm the homepage shows it after refresh. Toggle an existing photo off and verify gallery and full-screen browsing skip it; this is presentation only, not a way to remove public files or protect private images. Restore the photo afterward.

Historical summaries: create a draft ONLY for a concluded incident independently determined appropriate for public release. The record contains just a general category, staff UID and draft creation time. Do not add private source material, actual incident times, names, addresses, incident IDs or dispatch notes. A different authorized staff account may approve only after 24 hours; rules enforce the delay and the atomic draft/public record transition. Public record includes only the category and publication timestamp (not incident time); the public app shows the publication date and broad Western New York region for up to seven days. No automatic Active911 feed import or ongoing scene information. The original reviewed JSON feed remains independent. Unpublishing deletes the public copy, not the private published draft. Publication and withdrawal cannot undo prior public access. Verify self-approval, early approval, arbitrary fields and direct publication are denied; then test a separate authorized reviewer after the hold. Use a separate test project for fictitious drafts, never publish fictional records in the public project. Keep records minimal and remove obsolete private drafts through the owner console per your retention policy.

Notifications: the existing Settings test still works as before. Remote sending, free-form announcements, user management inside the app, photo uploads, vote administration and full analytics are not implemented. No service account credentials belong in a browser or public repository. The admin portal requires network access and uses session-scoped authentication; sign out on shared devices. App controls are not access controls by themselves: correct deployed Firestore rules are essential.

## Rollback
Restore previous versions of index.html, app.js, app.css, sw.js, push.js and README.md, and remove the new portal files. The dedicated Firebase project can be disabled independently without changing the original app's weather/voting/push data. No files from the old reviewed incident feed or gallery are included in this patch.
